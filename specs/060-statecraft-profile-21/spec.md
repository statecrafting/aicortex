# 060: Statecraft profile revision 21

## 1. Purpose

The owner decided on 2026-10-30 to adopt Statecraft github-actions-rust
revision 21 now, with spec-spine pinned at exactly `=0.31.0`. This spec
records Aicortex's migration consent for that move. It amends the revision 14
binding recorded by spec 054 and spec 001 without rewriting that approved
history. No Aicortex product behavior or acceptance authority is added.

## 2. Territory

This amendment owns no product code and grants no implementation claim. It
changes the adopted setup-profile revision and the exact engine pin only. The
managed files it regenerates stay in spec 001's authority, and existing owning
specs, workspace boundaries and specialized verification acceptance remain
unchanged.

## 3. Migration contract

The engine pin and the profile revision move in one change, because neither
can move alone: revision 21's producer links spec-spine-core 0.31.0 and its
plan withholds the whole profile while `spec-spine.toml` pins any other
version, and the revision 14 policy cannot install or judge a 0.31.0 corpus
whose shards carry the newer registry and index schema versions.

- `spec-spine.toml [meta] required_version` becomes `=0.31.0`, and every site
  that states the pin moves with it (spec 001 D-18). Spec-spine 0.32.0 is out
  of reach until a statecraft-cli release links spec-spine-core 0.32.
- Every registry and codebase-index shard is regenerated with 0.31.0.
- Managed setup artifacts are regenerated with the revision 21 producer
  through `statecraft-cli init plan` and `init apply --plan <identity>`, never
  edited by hand. The recorded setup parameters are kept: the extra required
  jobs `corpus-attestation`, `supply-chain` and `spec-dag`, the authored
  content checker over files and pull request text, enforced coverage, the
  per-commit gate, signed commits, and `@bartekus` code ownership.
- Aicortex keeps the ordinary Rust code gate. Every required job must still
  pass through the required `ci-gate`; cancellation, failure and an
  unexpected skip do not pass. The owner Environment approval path and the
  existing secret references are kept.
- The derived directory stays at `.derived/`. Revision 21 offers, but does
  not require, `statecraft-cli migrate apply` (the move to
  `.statecraft/derived/`); that move rewrites every in-flight branch and is
  separate work needing its own owner decision.

## 4. Acceptance criteria

- **AC-1.** The committed managed profile declares revision 21 and agrees
  with the recorded renderer identity, and a second `init plan` over the
  committed tree writes nothing.
- **AC-2.** The exact engine pin is `=0.31.0` in `spec-spine.toml` and every
  site that states it, and every shard is fresh under 0.31.0.
- **AC-3.** The ordinary Rust code job remains required together with the
  corpus attestation, supply chain and spec DAG jobs.
- **AC-4.** Local governance, postcommit coupling and every required hosted
  check pass for the integration candidate before merge.
- **AC-5.** No product code, trust root, secret value, spec lifecycle other
  than this spec's own, or branch-protection rule is changed by the migration.

## 5. Out of scope

The `.derived/` to `.statecraft/derived/` move; spec-spine 0.32.0; any change
to setup parameters; any remote setting. The remote obligations revision 21
lists are the owner's to keep and are reported, not applied, by this change.

## 6. Resolved decisions

- **D-1 (2026-10-30, owner decision, scope).** Adopt revision 21 now with the
  exact pin `=0.31.0`, in one pull request, rather than waiting for a
  statecraft-cli release that links spec-spine-core 0.32.
- **D-2 (2026-10-30, implementation, drifted managed workflows).** The
  revision 21 plan first reported `.github/workflows/statecraft-ci.yml` and
  `.github/workflows/statecraft-ai-review.yml` as customized conflicts: a
  Dependabot pull request had bumped their pinned `actions/checkout` from
  v7.0.0 to v7.0.1 by hand, so their bytes matched neither the recorded
  revision 14 digests nor the revision 21 render. A conflict keeps the edited
  file and leaves the profile unadopted, so those two files were restored to
  their recorded revision 14 bytes (commit `0fba391`) and the plan re-run; it
  then replaced them cleanly. Revision 21 itself pins checkout v7.0.0, so the
  rendered workflows carry v7.0.0 again. A later Dependabot bump of a managed
  workflow is drift the profile reports; the version moves when the profile
  moves it.
- **D-3 (2026-10-30, implementation, engine 0.30 and 0.31).** Regenerating
  under 0.31.0 changes only each shard's schema version (registry 1.9.0 to
  1.10.0, codebase index 1.2.0 to 1.3.0); `check` and `lint` stay clean at
  `--fail-on-warn` with no corpus edit.

## 7. Approval basis

Owner consent is the explicit owner decision of 2026-10-30 to adopt revision
21 with spec-spine pinned at exactly `=0.31.0`. This spec grants only that
scoped migration. It lands together with the migration, and the candidate
must pass its declared local and hosted acceptance before merge.
